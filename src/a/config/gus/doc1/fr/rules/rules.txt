@1 - Introduction
Les règles décrites ci-dessous sont liées à mon code source dérivé en tant que développeur gus, c'est à dire, mes composants noyau, entité et config.

Elles ne constituent pas des règles strictes mais plutôt des préconisations qui vous pouvez choisir de suivre ou non pour vos propres développements.

Chaque règle énoncée est identifiée par un numéro qui pourra être utilisé comme référence dans les autres documentations de la manière suivante : gus#1

@2 - Classification xyz des entités
Mes entités gus (à l'exception notable de ma première entité : gus.first) sont toutes classées en 3 catégories, x, y et z.

De manière générale, pour un développeur <pseudo> :
- Les entités x sont toutes les entités dont le nom commence par <pseudo>.x.<...>
- Les entités y sont toutes les entités dont le nom commence par <pseudo>.y.<...>
- Les entités z sont toutes les entités dont le nom commence par <pseudo>.z.<...>

Les entités x, y et z forment des regroupements nommés unités x, y et z, détaillées respectivement par les règles gus#3, gus#4 et gus#5.

@3 - Les unités x
Les unités x sont des "regroupements" composés chacun d'une entité unique et nommés ainsi :  <pseudo>.<...> (nom de l'entité sans la partie x)
Ces entités ne doivent pas faire appel à des services ou des ressources au moyen de la classe Outside. Elles peuvent en revanche faire appel à la méthode err de Outside.
Elles sont donc considérées comme autonomes

@4 - Les unités y
Les unités y sont des regroupements d'entités y dont le nom commence par <pseudo>.y.<y-part>.<...>, et nommés ainsi : <pseudo>.<y-part>
Les entités qui composent une unité y forment un ensemble cohérent et réutilisable. Elles peuvent faire appel à des services ou des ressources et ainsi créer des relations de dépendance avec d'autres entités d'unités x ou y quelconques. 
En revanche, elles ne doivent pas créer de dépendances avec des entités d'unités z.

Les unités y se divisent en :
- systèmes fonctionnels (cf gus#12)
- bibliothèques d'entités (cf gus#13)

@5 - Les unités z
Les unités z sont des regroupements d'entités z dont le nom commence par <pseudo>.z.<z-part>.<...>, et nommés ainsi : <pseudo>.<z-part>
Les entités qui composent une unité z sont dédiées à une application particulière identifiée par une config applicative <config-id> = <pseudo>.<z-part>. Elles peuvent faire appel à des services ou des ressources et ainsi créer des relations de dépendance avec d'autres entités notamment des entités d'unités x ou y quelconques. En revanche, elles ne doivent pas créer de dépendances avec des entités d'autres unités z.
Par exemple, l'unité z gus.appli1 est liée à l'application et la config applicative du même nom, et regroupe les entités dont le nom commence par gus.z.appli1.

On notera que les entités d'une unité z sont spécifiques à une application et qu'il faut essayer de limiter leur importance au strict minimum.
Si la première phase de développement applicatif en mode "quick and dirty" conduit à une unité z conséquente, il faudra essayer de refactorer son code a posteriori pour tenter d'en convertir certaines parties en unités y réutilisables. 

@6 - doc1
La documentation du développeur <pseudo> :

Cette documentation est regroupée à l'intérieur du composant config <pseudo>.doc1, de la manière suivante :

Pour une langue donnée, identifiée par une locale <loc> (fr pour le français), on aura :
- La documentation des applications dans : a.config.<pseudo>.doc1.<loc>.app
- La documentation des règles dans : a.config.<pseudo>.doc1.<loc>.rules
- La documentation des configs dans : a.config.<pseudo>.doc1.<loc>.src.config
- La documentation des noyaux dans : a.config.<pseudo>.doc1.<loc>.src.core
- La documentation des entités dans : a.config.<pseudo>.doc1.<loc>.src.entity

Les fichiers de documentation situés dans ces packages sont des fichiers texte respectant le format suivant :
- Une succession de sections délimitées par des lignes de titre qui commencent toutes par un unique arobas
- Des blocs de texte multilignes entre les titres qui correspondent au corps des sections

Le titre d'une section prend une forme différente selon la catégorie de documentation :
- Pour le fichier rules.txt, le titre est de la forme <rule-num> - <rule-title> (cf gus#14)
- Pour les fichiers de documentation d'une unité x, y ou z (cf gus#11), le titre est simplement le nom d'un champ décrivant l'unité, et le corps de la section est la valeur de ce champ (cf gus#29 pour la liste des champs)

@7 - doc1/app
Documentation des applications du développeur <pseudo> :

Pour une application identifiée par config <config-id> = <pseudo>.<config-part>, la documentation correspondante est stockée dans le package racine dédié : a.config.<pseudo>.doc1.<loc>.app.<config-part>
Par exemple, la documentation française de l'application gus.appli1 est stockée dans a.config.gus.doc1.fr.app.appli1

Elle se répartit en 3 fichiers texte : 
- doc_tech.txt : fichier contenant la documentation technique de l'application
- doc_user.txt : fichier contenant le manuel utilisateur de l'application
- changes.txt : fichier retraçant les changements au fil des différentes versions (améliorations, corrections de bugs...)

@8 - doc1/rules
Documentation des règles du développeur <pseudo> :

Elle se compose d'un unique fichier rules.txt contenu dans le package a.config.<pseudo>.doc1.<loc>.rules
Le fichier que vous êtes actuellement en train de lire en est un exemple, situé dans le package a.config.gus.doc1.fr.rules

@9 - doc1/config
Documentation des configs du développeur <pseudo> :

Chaque composant config d'ID : <config-id> = <pseudo>.<config-part> est documenté dans un fichier <config-part>.txt situé dans le package a.config.<pseudo>.doc1.<loc>.src.config
Par exemple, la documentation française de ma config gus.doc0 est contenue dans le fichier doc0.txt du package a.config.gus.doc1.fr.src.config

@10 - doc1/core
Documentation des noyaux du développeur <pseudo> :

Chaque composant noyau : <core-name> = <pseudo>.<core-part> est documenté dans un fichier <core-part>.txt situé dans le package a.config.<pseudo>.doc1.<loc>.src.core
Par exemple, la documentation française de mon noyau gus.gyem est contenue dans le fichier gyem.txt du package a.config.gus.doc1.fr.src.core

@11 - doc1/entity
Documentation des entités du développeur <pseudo> :

Les unités x sont documentées dans des fichiers dédiés, situés dans le package a.config.<pseudo>.doc1.<loc>.src.entity.x, et nommés <entity-parts>.txt (ou <entity-parts> correspond ici aux parties du nommage de l'entité après <pseudo>.x)
Par exemple, la documentation française de l'unité x gus.app.location est contenue dans le fichier app.location.txt du package a.config.gus.doc1.fr.src.entity.x

Les unités y sont documentées dans des fichiers dédiés, situés dans le package a.config.<pseudo>.doc1.<loc>.src.entity.y, et nommés <system-part>.txt (ou <system-part> correspond ici à la partie des nommages d'entités juste après <pseudo>.y)
Par exemple, la documentation française de l'unité y gus.swing1 est contenue dans le fichier swing1.txt du package a.config.gus.doc1.fr.src.entity.y

Les unités z sont documentées dans des fichiers dédiés, situés dans le package a.config.<pseudo>.doc1.<loc>.src.entity.z, et nommés <app-part>.txt (ou <app-part> correspond ici à la partie des nommages d'entités juste après <pseudo>.z)
Par exemple, la documentation française de l'unité z gus.appli1 est contenue dans le fichier appli1.txt du package a.config.gus.doc1.fr.src.entity.z

@12 - systèmes fonctionnels
Un système fonctionnel est un type particulier d'unité y pour lequel les entités s'articulent autour d'une au plusieurs fonctionnalités formant un tout cohérent.
Les unités y s'appellent les unes les autres, vérifient un ensemble de spécifications formalisées par des règles numérotés, et proposent des mécanismes réutilisables et extensibles dont l'étude fera l'objet de prochaines sections.

@13 - bibliothèques d'entités
Une bibliothèque d'entités est un type particulier d'unité y pour lequel les entités ne s'articulent pas autour de fonctionnalités mais partagent une même thématique tout en restant largement indépendantes les unes des autres.
Tout comme les systèmes fonctionnels, ces unités vérifient un ensemble de spécifications dans le but de les rendre le plus générique possible, et donc réutilisables.
Un exemple de bibliothèque est l'unité y gus.convert1 qui regroupe des entités T permettant de convertir des objets java.

@14 - Identification des règles
Les règles édictées par chaque développeur sont identifiées par un identifiant unique composé comme suit :
<rule-id> = <pseudo>#<rule-num> ou <rule-num> est le numéro de la règle dans la numérotation interne au développeur.

Les règles expliquent des mécanismes généraux partagés par un grand nombre de composants (entités, noyaux, configs), du développeur lui-même ou d'autres développeurs.
Elles peuvent notamment être référencés par d'autres règles et apparaître dans les spécifications liées à des unités x, y ou z.

Comme indiqué en règle gus#8, les énoncés des règles sont regroupés dans le fichier rules.txt du package a.config.<pseudo>.doc1.<loc>.rules, qui est structuré en sections avec des lignes de titre débutant par un arobas. Ces sections sont rangées dans l'ordre des numéros avec des titres comme suit :
<section-title> = <rule-num> - <rule-title>
ou <rule-title> est le titre de la règle.

@15 - keys dans la feature R
Lorsqu'on a une implémentation de R qui accepte des clés spécifiques, il faut éviter d'utiliser la clé "keys" qui est une clé technique qui doit, elle, renvoyer le tableau String[] des autres clés acceptées.

@16 - Outside.err
Lorsque le code d'une méthode private doit gérer des exceptions au moyen d'un unique bloc try-catch, le catch doit renvoyer l'exception vers le noyau en appelant la méthode statique Outside.err. L'id passé en paramètre doit alors être le nom de la méthode private (avec ses types de paramètre éventuels).

Voici un exemple :

private void perform(String data) {
	try { ... }
	catch(Exception e) {Outside.err(this,"perform(String)", e);}
}

@17 - S1 send event
Lorsqu'une entité qui hérite de S1 doit envoyer un évènement, il faut écrire une méthode private sans paramètre, dédiée à l'envoi de cet évènement, ou l'id passé dans send correspond au nom de la méthode.

Voici quelques exemples :

private void modified() {
	send(this,"modified()");
}
private void added() {
	send(this,"added()");
}
private void removed() {
	send(this,"removed()");
}

@18 - règle d'icône
Une règle d'icône permet de générer une icône 16x16 (classe Icon)

Le mécanisme qui génère une icône à partir d'une règle doit disposer d'un ensemble d'icônes identifiées par des IDs. Il doit aussi être capable de retrouver l'icône associée par l'OS à une extension de fichier.

Mécanisme de niveau 1 : <icon-rule1> = <icon-id> | FILE_<file-ext>
Si la règle correspond à un ID connu d'icône, celle-ci est renvoyée.
Si la règle est de type FILE_<file-ext>, alors l'icône OS associée à l'extension <file-ext> est renvoyée.

Mécanisme de niveau 2 : <icon-rule2> = <icon-rule1>_<suffix-part>
où <suffix-part> est une String sans underscore tel que PART_<suffix-part> correspond à un ID d'icône (qui est associée au suffixe).
Si la dernière partie de la règle est un suffixe <suffix-part>, alors l'icone renvoyée est la superposition de l'icône principale (règle <icon-rule1>) et de l'icône du suffixe.

Voici un exemple :
Si BASE et PART_add sont des ID d'icônes, alors la règle BASE_add renverra comme icône la superposition des icônes de BASE et PART_add.

@19 - règle de display graphique
Une règle de display graphique permet d'associer une icône et un libellé comme ceci :
<display-rule> = <icon-rule>#<label>

@20 - Les icônes d'une config
Une config <config-id> peut proposer des icônes, stockées au format GIF à la racine de son sous-répertoire icon (correspondant au package a.config.<config-id>.icon). 
Chaque fichier GIF ainsi chargé par le noyau correspondra à un ID unique <icon-id> égal au nom du fichier sans l'extension, et correspondra donc au chemin local suivant :
/a/config/<pseudo>/<config-part>/icon/<icon-id>.gif

@21 - Les appels de ressource
Toute entité peut potentiellement appeler une ou plusieurs ressources depuis sa classe principale de la manière suivante :
Object r = Outside.resource(this, "<call>");
ou <call> est une String plus ou moins complexe pouvant correspondre à un ID ou une règle, et sensé décrire la ressource dont l'entité a besoin.

Le composant noyau qui gère l'application doit alors être en mesure d'interpréter <call> pour construire ou fournir la ressource adéquate. Il devra être capable de s'adapter à n'importe quelle entité en disposant d'un mécanisme suffisamment flexible et paramétrable pour répondre correctement à ces différents appels.

Les règles dont le titre débute par "call :" sont des règles de spécification d'appels qui peuvent être prise en compte aussi bien par des entités que par des noyaux.
Si une telle règle est partagée par une entité et un noyau (cf. documentations respectives), alors l'appel correspondant n'aura pas besoin de paramètrage pour fonctionner. Dans le cas contraire, le noyau devra impérativement disposer d'un mapping établissant la correspondance entre l'appel et la règle de génération de la ressource attendue, comme par exemple :
<entity-name>@<call> = <resource-rule>

Pour une application donnée, la config applicative associée aura la responsabilité de fournir ce mapping, afin d'assurer à toutes les entités utilisées que leurs appels seront correctement gérés par le noyau.

@22 - Les appels de service
Toute entité peut potentiellement appeler un ou plusieurs services depuis sa classe principale de la manière suivante :
Service s = Outside.service(this, "<call>");
ou <call> est une String plus ou moins complexe pouvant correspondre à un ID ou une règle, et sensé décrire le service dont l'entité a besoin.

En fait, il s'agit du même mécanisme que pour les appels de ressource, à ceci près que l'objet généré est supposé implémenter une ou plusieurs interfaces standards du framework a, et qu'il est préalablement transformé en Service au moyen d'une classe enveloppe qui implémente l'interface Service. Voici un exemple de ce que cela peut donner :

public class ServiceImpl implements Service {
	private Object resource;
	
	public ServiceImpl(Object resource) {
		this.resource = resource;
	}
	public void e() throws Exception {
		((E) resource).e();
	}
	...
}

En pratique : 
- les appels de service correspondront à des règles qui renvoient des instances d'entités ou d'objets propres au noyau. 
- les appels de ressource correspondront à des règles renvoyant tous les autres types d'objet Java (List, Map, Icon, String, File...)

@23 - call : mécanisme général
Le mécanisme de gestion des appels de resources (et de services) peut rencontrer 3 cas de figure :

1: la règle correspond à l'ID d'un objet déjà existant, connu du noyau. Dans ce cas, cet objet est renvoyé à l'entité.
Exemple : Service entityToName = Outside.service(this, "m042.t.entity.findname");

2: la règle correspond à un nom d'entité (à quelques variantes près qu'on verra plus tard). Dans ce cas, une instance de l'entité est renvoyée à l'entité.
Exemple : Service s = Outside.service(this, "*gus.x.swing.panel.bg.blue");

3: la règle est de type <provider-name>#<resource-info>. Dans ce cas, le noyau est sensé disposer d'un fournisseur de ressource identifié par <provider-name>. Il va alors demander à ce fournisseur de fournir la resource, en lui passant notamment en paramètre <resource-info>
Exemple : Icon icon = (Icon) Outside.resource(this, "icon#monIconId");

Ces explications donnent un cadre général à la manière dont le noyau doit gérer les appels (qui sera précisé par la suite). Ce cadre pourra bien-sûr varier d'un noyau à l'autre (cf. documentations de chaque noyau).

@24 - Mécanismes d'extension d'un système fonctionnel

Un système fonctionnel peut prévoir un ou plusieurs mécanismes d'extension, permettant d'ajouter de nouveaux comportements sans toucher au cœur du système. Une extension est toujours une unité x ou y, jamais z : elle doit
rester réutilisable indépendamment de toute application particulière.

On distingue deux types de mécanismes :

- Extension interne : l'unité d'extension est une dépendance directe et codée en dur du système. Ajouter un cas nécessite de modifier le code du système pour y référencer la nouvelle unité. Le système est donc extensible au
codage (maintenabilité), mais pas au runtime.

- Extension externe : l'unité d'extension n'est pas liée en dur au système mais injectée dans celui-ci. On l'appelle alors un plugin. 
Cette injection peut se faire de deux manières :
- par un appel externe à une caractéristique du système (généralement P ou V) afin de lui communiquer l'objet plugin (cas le plus courant)
- par un appel interne à un service du système, qui va communiquer l'ensemble des objets plugin disponibles (cas plus rare)

Contrairement à l'extension interne, un mécanisme de plugin est extensible au runtime : on peut lui injecter de nouveaux plugins sans modifier ni recompiler son code.

@25 - Unité wrapper pour injecter des plugins

Une unité wrapper (y ou z) peut être mise en place pour injecter des plugins dans un système fonctionnel qui propose un mécanisme de plugin.

Ce schéma permet de découpler deux niveaux d'appel :
- le système fonctionnel initial reste appelable indépendamment, avec injection dynamique de n'importe quel plugin
- l'unité wrapper est appelée quand on veut une fonctionnalité "out of the box", déjà préconfigurée.

@26 - Multiplicité d'une entité

La multiplicité n'a de sens que dans le contexte d'utilisation d'une entité par le noyau : elle indique si le noyau renvoie la même instance de l'entité à chaque appel, ou une instance distincte à chaque appel. Deux valeurs sont possibles :
- unique (+) : le noyau renvoie la même instance de l'entité à chaque appel.
- multiple (*) : le noyau renvoie une instance distincte de l'entité à chaque appel.

Il s'agit donc d'une règle de paramétrage du noyau concernant l'usage d'une entité, et non d'une propriété intrinsèque de celle-ci.

En pratique, la multiplicité effective est portée par l'entité appelante, via le préfixe de la string d'appel utilisée pour Outside.service()/Outside.resource() : l'absence de préfixe vaut unique (règle par défaut), le préfixe `*` vaut multiple. Cette règle par défaut peut être surchargée dans la configuration du noyau.

La multiplicité indiquée dans le sign (documentation) de l'entité appelée n'est donc qu'une indication non contraignante de son usage de prédilection — elle ne pilote pas directement le comportement du noyau.

Le caractère stateless d'une entité (aucune variable de niveau classe, hors static final) induit une multiplicité unique de prédilection. La réciproque est fausse : une entité stateful peut elle aussi avoir une multiplicité unique de prédilection, lorsque son état de classe peut être considéré comme un singleton partagé sans risque par toute l'application (ex. cache lazy d'une valeur idempotente).

@27 - Signature simple d'une entité

La signature simple d'une entité est une notation compacte formée de sa multiplicité (cf gus#26) suivie des lettres des features qu'elle implémente, parmi les 11 interfaces standardisées du framework (cf a_fr_framework#002). Les lettres sont toujours en majuscules et triées par ordre alphabétique, afin de normaliser la signature (une même entité ne peut avoir qu'une seule signature simple possible).

Format : <multiplicité><features>

Voici un exemple : une entité de multiplicité unique implémentant E, T et V aura pour signature simple : +ETV

@28 - Signature complète d'une entité

La signature complète d'une entité reprend la signature simple (cf gus#27) en ajoutant, pour certaines features, une annotation de type entre chevrons accolée directement à leur lettre :
- E, B, H, S : jamais de type
- G, I : <type-retour>
- P, F : <type-entrée>
- R : <type-retour> (la clé est toujours une String, elle n'est pas indiquée)
- V : <type-valeur> (la clé est toujours une String, elle n'est pas indiquée)
- T : <type-entrée,type-sortie>, ou juste <type> si l'entrée et la sortie sont de même type

Règles d'annotation :
- utiliser le nom simple du type java le plus précis possible (String, File, List, Icon...)
- si le type ne peut pas être déterminé avec certitude, ne pas l'annoter et laisser la lettre seule (comme en signature simple)
- si plusieurs types sont possibles pour une même entrée/sortie, les séparer par un | et les trier par ordre alphabétique
- ne jamais indiquer null comme type possible

Voici un exemple : une entité de multiplicité multiple implémentant E (jamais typée), V (acceptant une valeur de type String ou File) et T (prenant une String et retournant soit une String soit un Double) aura pour signature complète : *EV<String|File>T<String,String|Double>

@29 - Champs de documentation d'une unité

Une unité x, y ou z est décrite par un ensemble de champs, stockés selon le format défini en gus#6. Voici la liste des champs actuellement définis :

Champs communs à toute unité (x, y ou z) :
- description : présentation de l'unité
- state : GENERATED ou COMPLETE
- tags : mots-clés ASCII majuscules, séparés par une virgule
- difficulty : niveau de 0 à 3
- generator, generated_time : présents uniquement si state=GENERATED
- comment : notes libres, optionnel

Champs spécifiques à une unité x :
- sign : signature complète de l'entité (cf gus#28)
- creation_date : date de création de l'entité

Champs spécifiques à une unité y :
- type : LIBRARY ou FUNCTIONAL (cf gus#12/#13)
- sign : uniquement si type=LIBRARY, signature générique partagée par tous les membres
- index : uniquement si type=LIBRARY, une ligne <partie-variable-du-nom>=<description brève> par entité membre
- members : uniquement si type=FUNCTIONAL, liste des entités membres du système, une par ligne
- entry : uniquement si type=FUNCTIONAL, la ou les entités point(s) d'entrée
- extension : uniquement si type=FUNCTIONAL et le système propose un ou plusieurs mécanismes d'extension (cf gus#24) — le champ est répété une fois par mécanisme, chaque occurrence précisant en texte libre : mechanism (nom court, si plusieurs mécanismes), kind (EXTENSION pour une extension interne, ou PLUGIN pour une extension externe — cf gus#24 pour la distinction), direction (INTERNAL ou EXTERNAL, uniquement si kind=PLUGIN), une description du mécanisme, et spec (codes de règles concernées, séparés par ;)
- registry_queryable : uniquement si type=FUNCTIONAL avec un mécanisme kind=PLUGIN, indique si la liste des plugins enregistrés est interrogeable (YES ou NO)

Une unité z ne comporte aucun champ spécifique : n'étant pas destinée à être réutilisée (cf gus#5), les champs qui documentent la manière d'utiliser une unité (type, sign, index, members, entry, extension, registry_queryable) n'ont pas de sens pour elle. Seuls les champs communs s'appliquent.
